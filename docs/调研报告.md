# 调研报告：市面上有没有"学生传 PPT、老师看进度"的现成系统？

调研时间：2026-11。目标场景：课题组每周组会，学生各自把本周汇报 PPT 放到自己的**私有仓库**，老师集中查看每人每周的进展与 PPT 内容，公网可访问。

## 一、结论先说

**没有完全对口的产品**，但有几类"半对口"方案，各有明显缺口：

| 类别 | 代表 | 差在哪 |
|---|---|---|
| GitHub 官方教育产品 | GitHub Classroom | 为**代码作业**设计：能看提交状态、跑自动评测，但不擅长"每周一份 PPT + 进展说明"的例行汇报；且需要教师资质审核 |
| 教育类开源监控 | Git4School、repobee、github-classroom-utils | 盯的是 commit / 题目完成率，不看汇报内容，也没有 PPT 视图 |
| 贡献可视化 SaaS | GitLeader | 只统计 commit、PR 数量，回答不了"这周他做了什么、PPT 讲了什么" |
| 协作套件模板 | 飞书汇报、Notion 团队周会模板 | 体验成熟，但把**汇报和生产资料（代码、实验、PPT）分家**，老师要在第二套系统里重新登录、重新找文件 |
| 通用 LMS | Canvas / Blackboard / Moodle | 作业提交能力有，但为课程评分设计，课题组周会用它太重 |

因此本次选择**自建一层轻量胶水**：文件存 GitHub 私有仓库（权限、版本历史、diff 全部白送），汇总交给 GitHub Actions，展示交给 GitHub Pages。真正需要自己写的只有"汇总 + 看板"这一小段。

## 二、逐个看

### 1. GitHub Classroom（最接近，但不是它）

学生通过邀请链接接受作业，GitHub 自动为每人创建**私有仓库**；教师端有一个 Classroom dashboard，列出谁接受了、谁提交了，一键跳到每个学生的仓库，还能在 PR 上做行内评论、跑 autograding。

- 优点：权限模型、私有仓库、教师总览都是现成的，和 GitHub 账号体系天然打通。
- 缺口：
  - 作业是"一次性"的，一个 assignment 对应一个仓库；组会是"每周一期"，用 Classroom 得每周建一次 assignment，学生每周重新接受，操作繁琐。
  - 没有"PPT 内容"视图：只能看到文件列表，PPT 要下载下来自己开。
  - 没有周次矩阵、迟交判定、连续掉队提醒这类"周报语义"。
  - 教师身份需要 GitHub Education 审核。
- 参考：<https://archfx.me/posts/2025/12/classroom/>、<https://www.nitic.org/using-github-classroom-for-software-development-instruction/>

### 2. Git4School

法国教学场景的开源工具，教师实时跟踪学生在实践课上的 commit 曲线、题目完成率、commit 类型分布。

- 优点：把"commit 行为"可视化成教学信号，思路值得借鉴（本方案里的"提交时间"判定就来自类似逻辑）。
- 缺口：面向课堂练习（TP），没有"每周汇报文件"的概念，也没有 PPT 预览。
- 参考：<https://git4school.github.io/>

### 3. GitLeader

商业 SaaS，连接 GitHub 组织后给出私有排行榜：谁在提交、哪些仓库有热度、周/月/全周期贡献对比。

- 优点：零配置、默认私有，团队贡献一目了然。
- 缺口：只回答"提交了多少"，不回答"讲了什么"；按人头排名对课题组容易导向错误的激励；需要付费订阅。
- 参考：<https://gitleader.com/>

### 4. repobee / github-classroom-utils

CLI 工具，批量创建/管理学生仓库、批量拉取、统计提交时间（甚至有专门检测"改提交时间"的脚本）。

- 优点：批量管理省事，适合 50 人以上。
- 缺口：纯命令行，没有给老师看的界面；要自己写脚本串起来。
- 参考：<https://github.com/repobee/repobee>、<https://github.com/danwallach/github-classroom-utils>

### 5. 飞书汇报 / Notion 团队周会模板

- 飞书汇报可以配置周报规则、模板、提醒，统计谁没交，管理端体验很好。
- 缺口：PPT 是附件或云文档，**和生产资料（代码、实验数据、版本历史）分离**；课题组往往本来就在 GitHub 上干活，等于多维护一套系统；私有化部署成本高。
- 参考：<https://www.feishu.cn/hc/zh-CN/articles/360043028774>、<https://www.notion.com/zh-cn/templates/category/team-weekly>

### 6. 自建：Actions + Pages（本方案）

| 维度 | 表现 |
|---|---|
| 私有仓库 | 每学生一个，权限天然隔离，老师是组织 owner 可见全部 |
| 版本历史 | 白送：谁什么时候交的、改了哪些页，`git log` 可查 |
| 老师总览 | 学生 × 周次矩阵 + 本周进展卡片 + PPT 文本预览 |
| 登录 | 老师用自己已登录的 GitHub 账号（点链接即看原件），无需在第三方系统再注册 |
| 部署成本 | 0 台服务器、0 个域名；Pages + Actions 免费额度足够（私有仓库每月 2000 分钟 Actions） |
| 缺口 | Pages 只能从 public 仓库发布（Free 计划），所以汇总数据是公开的 → 默认只放"谁交了、什么时候、文件名"，不放正文 |

## 三、为什么最终选这条路

1. **数据本来就在 GitHub**：学生的代码、实验记录、PPT 都在私有仓库里，再搬去 Notion/飞书是重复劳动，还容易不同步。
2. **权限不用自己写**：私有仓库 + 组织成员 + collaborator，就是最省事的 ACL；老师看原件天然有权限，看板只负责"导航"。
3. **零运维**：Actions 定时跑汇总，Pages 托管静态页，没有服务器要打补丁、没有数据库要备份。
4. **可演进**：真需要"页面内看 PPT 全文/评论/打分"时，把 `scripts/collect.mjs` 挪到一个有后端的环境即可，前端结构不用大改。
